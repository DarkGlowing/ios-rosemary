# Исправления для Rosemary (MT6785) — что сделано и что тестировать

Все адреса ниже **подтверждены по дампам с твоего телефона** (preloader boot1, lk_a, boot_a/kernel dtb), а не взяты из интернета.

## 1. Что исправлено / добавлено

### A. Поглаживание A7-WDT (авто-сброс сохранён, зависаний на экране нет)
- **Адрес подтверждён**: `A7_WDT = 0xf0400000` (3 вхождения в preloader).
- Файл: `shim/platform_mt6785.c` → `wdt_pet()`, `wdt_init_long_timeout()`.
- Вызывается:
  - в начале `shim_main()` — удлиняет таймаут и гладит сразу;
  - в `delay_ms()` — каждые ~5 секунд во всех ожиданиях (UFS probe 3 мин, удержание panic-экрана 40 с).
- **Важно**: WDT НЕ отключается. Если XNU/shim зависнет — поглаживания прекратятся, через ~60 с произойдёт аппаратный сброс и LK вернётся на слот A. Это желаемое поведение.

### B. EMI-restore перед сбросом (снижает риск «sending emi data»)
- **Адреса подтверждены**: `CEN_EMI=0x10219000`, `DRAMC0=0x10230000`, `DRAMC1=0x10240000`.
- Файл: `shim/platform_mt6785.c` → `emi_restore()`.
- Вызывается в `reset()` **перед** PSCI reset (значит, и на panic-пути через `exc_handler`, и при обычном завершении).
- Делает: вывод каналов DRAM из self-refresh, включение обоих каналов в EMI_CONA, пауза, поглаживание WDT.
- **Честно**: это НЕ полная перетренировка DRAM (её делает только preloader при холодном старте). Снижает вероятность зависания BROM на `sending emi data`, но 100 % гарантии нет. Финальный резерв — выключить телефон на 3–5 мин + SP Flash Tool.

### C. Framebuffer-консоль — код есть, факт успешного вывода на rosemary не подтверждён
- `FB_BASE = 0x7bd20000` совпадает с началом зарезервированной области framebuffer в дампе телефона; размер области — `0x22e0000`.
- `shim/console.c` предполагает 1080×2400, stride 4320 и 4 байта на пиксель. Сам архив телефона подтверждает базу/размер области, но не доказывает формат scanout и stride в момент handoff от ABL.
- Предыдущая версия заметки утверждала, что красная консоль уже отображалась и что LK оставляет DSI-панель инициализированной. В приложенных материалах нет лога или видео, подтверждающих это именно на rosemary; считать утверждение проверенным нельзя.
- Адреса DSI/RDMA/PWM из DTB полезны как справочные MMIO-адреса, но сами по себе не доказывают, что дисплейный тракт активен и framebuffer физически сканируется после handoff.

### D. Адреса загрузки в build.sh приведены к стоку Rosemary
- `--base 0x40000000 --kernel_offset 0x00080000` → kernel @ `0x40080000` (как в стоковом boot_a).
- `--ramdisk_offset 0x07c80000` → ramdisk @ `0x47c80000` (как в стоке).
- `--pagesize 2048` (сток MT6785, было 4096).
- Добавлен `platform_mt6785.c` в сборку.
- Подложен распакованный `dtb/boot_unpacked/dtb` (из твоего boot_a).

## 2. Изменённые файлы
- `shim/platform_mt6785.h` — новый (адреса + прототипы).
- `shim/platform_mt6785.c` — новый (WDT pet + EMI restore).
- `shim/shim.c` — include, `delay_ms` с поглаживанием WDT, `reset()` с `emi_restore()`, `shim_main` с `wdt_init_long_timeout()`.
- `shim/build.sh` — адреса mkbootimg + новый исходник.
- `dtb/boot_unpacked/dtb` — распакован из твоего boot_a.

## 3. Что тестировать (по шагам)

### Тест 1 — Сборка
```bash
cd shim && ./build.sh
```
Ожидание: собирается без ошибок, появляется `out/shim-boot.img`.

### Тест 2 — Запуск через payload (без записи во flash)
```bash
python mtk.py payload out/shim-boot.img   # или через твой обычный способ
```
Ожидание:
- На экране появляется **красный фон с жёлто-белым текстом** консоли shim (строки `SHIM`, `LOADER`, `UFS`...).
- Если есть payload XNU в ramdisk — загрузится он; если нет — shim сделает UFS probe и через 3 мин уйдёт в reset.
- **WDT**: экран не гаснет и телефон не перезагружается сам во время показа консоли (значит, поглаживание работает).

### Тест 3 — Panic-путь и авто-сброс
Если что-то пойдёт не так — экран станет **синим** (PANIC) с регистрами (ESR/ELR/FAR...). Держи 40 с:
- Ожидание: через 40 с произойдёт `emi_restore()` → PSCI reset → телефон сам перезагрузится в обычную систему (слот A).
- Проверь, что после этого **mtkclient подключается без зависания на `sending emi data`** (это проверит EMI-restore).

### Тест 4 — Если зависнет намертво
Не паникуй: WDT сработает сам через ~60 с (поглаживание прекратится). Если и это не помогло — зажми 3 кнопки ~20 с, а если BROM всё равно зависает на `sending emi data` — выключи телефон на 3–5 мин (холодный сброс питания EMI).

## 4. Чего НЕ сделано (и почему)
- Полная переинициализация DSI-панели — не нужна (LK уже включил панель). Понадобится только если будем выключать/включать дисплей из XNU.
- Извлечение DCS-последовательности панели `dsi_panel_k7_*` — требует дизассемблирования lcm-драйвера в LK. Для ранней отладки не нужно.
- Полная тренировка DRAM из preloader — невозможна из ядра (закрытые процедуры).

## 5. Резерв
- Образ `boot_safe_backup.img` держи наготове.
- Тесты делай на слоте B (не на A), чтобы сохранить авто-откат.
