# iOS 16 root на USB-C флешке (rosemary, MT6785): что возможно и как

Короткий ответ: **технически возможно, но это самый тяжёлый из вариантов носителя**
— и делать это надо в 4 этапа, из которых сейчас сделан и собран этап 0/1
(probe USB-хоста в шиме).

---

## 1. Чего сейчас нет (важное открытие)

Все USB-патчи, лежащие в `xnu/patches/0072..0081` (`rosemary_usb*`), — это код,
перенесённый из порта `ios-sweet`, и он **Qualcomm-овский**:

| что в коде | для чего | на rosemary |
|---|---|---|
| `DWC3_PA 0x0a600000` | DWC3 у SM7125 | блока нет |
| `QSCRATCH_PA 0x0a6f8800` (0074) | Qualcomm-обёртка | блока нет |
| `GCC_PA 0x00100000`, `USB30_PRIM_GDSCR` | Qualcomm GCC | блока нет |
| `QUSB2_PA 0x088e2000` | Qualcomm QUSB2 PHY | блока нет |

То есть `rosemaryusb=2` на rosemary не «не поднялся» — он стучался в
несуществующие регистры. Это надо переписать целиком, что и сделано для
этапа 0/1 (см. §3).

## 2. Адресная карта USB на rosemary (из живого `dtb` телефона)

```
/usb3@11200000        reg 0x11200000 0x10000   xHCI (0x0000..) + DWC3 global/device (0xc1xx..)
/mtu3_0@11200000      reg 0x11201000 0x3000    MTK MAC glue
                      reg 0x11203e00 0x0100    "ippc" (USB3 switch / port control)
/usb3_phy, /usbphy0   reg 0x11e40000 0x10000   MTK U3PHY (в нём же USB2 PHY)
/spm@10006000         PWR_STATUS 0x0160        питание домена USB
/usbpd_pm, mt6360_pmu_chg, ln8000_charger       VBUS/OTG boost (PMIC, pwrap/SPMI)
```

Контроллер — стандартный Synopsys DWC3 с xHCI-интерфейсом, и это единственная
причина, по которой задача вообще решаема: **xHCI — стандарт**, а не проприетарный
контроллер. Всё, что нужно от MTK, — это включить питание/клоки и заставить
PHY работать в host-режиме.

`GSNPSID` (0xc120) в этапе 0 сразу скажет, живой ли блок и какая ревизия ядра.

## 3. Что уже сделано в этом заходе (можно проверить за 30 секунд)

Новые файлы (собираются локально, без CI):

- `shim/usb.c`, `shim/usb.h` — probe DWC3/xHCI по адресам выше;
- `shim/build.sh` — новый образ `out/shim-usbdiag.img` (`-DSHIM_USBPROBE`);
- `shim/shim.c` — блок `#ifdef SHIM_USBPROBE` (кадр + `usb_probe(1)` + hold 30 с).

Этап 0 (только чтение): SPM PWR_STATUS, xHCI CAPLENGTH/HCSPARAMS1/HCCPARAMS1,
DWC3 GSNPSID/GCTL/GUSB2PHYCFG0/GUSB3PIPECTL0/DCTL/DSTS, PORTSC1/2, glue IPPC.
Этап 1 (запись): `GCTL[13:12]=01` (host) → `DCTL.CSFTRST` → ожидание новой роли →
`PORTSC.PP=1` → опрос `PORTSC.CCS` 2 с.

Дисциплина отладки: **маркер печатается до доступа к регистру**. Если доступ
повесит шину (гейтед-клок), последняя строка на экране назовёт конкретный шаг —
это и есть результат, а не «просто чёрный экран».

Проверка:

```sh
cd work/ios-rosemary-reviewed-gic-console/ios-rosemary-main/shim && ./build.sh
# образ: shim/out/shim-usbdiag.img (gzip-ядро внутри, как требует LK)
```

```sh
fastboot getvar current-slot          # прошивать в активный слот
fastboot set_active a                 # если активен не a
fastboot flash boot shim/out/shim-usbdiag.img    # или boot_a по current-slot
fastboot reboot
```
Откат: `fastboot flash boot_a dump/boot_a.bin`.

Что читать с экрана:

| на экране | вывод |
|---|---|
| `gsnpsid=5533xxxx` и `caplen=40` | блок включён, это DWC3, можно идти дальше |
| `gsnpsid=0` / мусор | питание/клоки USB выключены после LK → нужен bring-up клоков |
| `prtcap=1` после сброса | host-режим взят |
| `DEVICE CONNECTED` | VBUS есть, PHY работает в host → этап 2 (enumeration) |
| `no connect` при `prtcap=1` | нет 5 В на VBUS (см. ниже) |

## 4. VBUS: два пути

1. **Питаемый USB-хаб / OTG-переходник с внешним питанием** (без кода): флешка
   получает 5 В от хаба, телефону остаётся только host-роль. Это то, с чего надо
   начинать — убирает из уравнения весь PMIC.
2. **OTG boost через MT6360** (нужен драйвер I2C/SPMI + запись в регистры
   charger): `mt6360_pmu_chg` в DTB, шина — pwrap/SPMI. В XNU уже есть
   `rosemary_spmi_read()` и `rosemary_pwrap_write16()` (патч 0062), так что
   технически это 1–2 дня, но требует сверки регистров MT6360.

## 5. Полный план до «iOS грузится с флешки»

| этап | что | где | объём | критерий готовности |
|---|---|---|---|---|
| 0/1 | probe + host mode + CCS | шим | **сделано** | `DEVICE CONNECTED` на экране |
| 2 | enumeration: enable slot, Address Device, GET_DESCRIPTOR, bulk endpoints | шим | 2–3 дня | VID/PID флешки и её объём на экране |
| 3 | BOT/SCSI: INQUIRY, READ CAPACITY, READ(10); кэш-операции | шим | 2–3 дня | чтение MBR/сигнатуры HFS+ с флешки на экране |
| 4 | то же в ядре: `bsd/dev/rosemary_usbmsc.c` → `IOBlockStorageDevice` `usbroot0`, `rd=usbroot0` в `IOKitBSDInit` | XNU (CI) | 3–5 дней | `BSD root: usbroot0` + `hfs: mounted` |

Итого честно: **1.5–3 недели** циклами «прошил → фото экрана → правка», против
≈3–5 дней на microSD (`msdc1@0x11240000`, уже разобранный в DTB) и ≈2 дней на
UFS-срез (если согласиться на усечение F2FS).

Почему всё равно может иметь смысл: флешку **не надо прошивать в телефон** —
образ корня готовится на ПК и пишется `dd`; итерации по образу бесплатные,
`userdata` не трогается вообще.

Ограничения, которые останутся и после этапа 4:
- флешка должна быть воткнута **до** загрузки (hotplug не нужен и не будет);
- только Bulk-Only Transport, один LUN, без хабов в цепочке (начнём с прямого порта);
- USB 2.0 High-Speed (480 Мбит/с ≈ 30–40 МБ/с реальных) — для HFS+ этого хватает;
- USB3/SS PHY (`0x11e40000`, SuperSpeed) не трогаем вообще.

## 6. Как поставить iOS 16.5 на флешку (после этапа 3)

Порядок не зависит от того, куда пишется образ: `userdata`, microSD или флешка.

### 6.1 Скачать IPSW

Нужен IPSW **iPhone X (iPhone10,3)** — порт выдаёт себя за D22AP/iPhone10,3
(`/device-tree/compatible`). Для iOS 16.5 это сборка **20F66**
(16.5.1 — 20F75; можно взять и её, но не смешивать).

### 6.2 Достать три DMG из IPSW

Имена лежат в `BuildManifest.plist` (`BuildIdentities[*].Manifest.<...>.Info.Path`):

```sh
mkdir -p ~/ios165 && cd ~/ios165
unzip -j ~/iPhone10,3,iPhone10,6_16.5_20F66_Restore.ipsw \
      'BuildManifest.plist' '*.dmg' -d .
python3 - <<'EOF'
import plistlib
m = plistlib.load(open('BuildManifest.plist','rb'))
for bid in m['BuildIdentities']:
    for k, v in bid['Manifest'].items():
        p = v.get('Info', {}).get('Path', '')
        if p.endswith('.dmg'):
            print(f"{k:28s} {p}")
EOF
# OS (rootfs) / SystemOS / AppOS — переименовать в OS.dmg, SystemOS.dmg, AppOS.dmg
```

OS-образ — UDIF (`koly`), криптексы — сырой APFS; `mkiosroot.sh` это учитывает
(имя файла должно кончаться на `.dmg`).

### 6.3 Собрать HFS+ корень (16 ГБ, case-sensitive, журналируемый)

```sh
cd work/ios-rosemary-reviewed-gic-console/ios-rosemary-main
sudo tools/mkiosroot.sh ~/ios165/OS.dmg ~/ios165/SystemOS.dmg ~/ios165/AppOS.dmg \
     ~/ios165/root-16.5.img 16G
sudo fsck.hfsplus -fy ~/ios165/root-16.5.img
sudo mount -t hfsplus -o loop,force ~/ios165/root-16.5.img /mnt/iosroot
sudo python3 tools/rosemary-root-tweaks.py /mnt/iosroot
sudo umount /mnt/iosroot
```

`tools/rosemary-root-tweaks.py` писался под 20H392 (16.7.16) и содержит
bring-up правки, которые на sweet оказались обязательными: пропуск Setup,
посев activation state, удаление baseband-демона, отключение вотчдогов,
некоторые media-пути. Для 16.5 их нужно прогнать и посмотреть, что скрипт
не нашёл — это отдельный источник ошибок, не связанный с USB.

### 6.4 Записать образ на флешку (Linux, никакого fastboot)

```sh
lsblk                              # найти флешку, например /dev/sdX (НЕ раздел!)
sudo dd if=~/ios165/root-16.5.img of=/dev/sdX bs=4M conv=fsync status=progress
# флешка стала «сырым» томом HFS+ с offset 0 — так его и будет читать драйвер
```

Проверка с хоста: `sudo fsck.hfsplus -fn /dev/sdX` (read-only).

### 6.5 Загрузка

Boot-args (меняются в `/tmp/cmdline.txt`, его читает `build-out/rebuild-xnu.sh`):

```
debug=0xc serial=3 cpus=1 keepsyms=1 -enable_kprintf_spam -noprogress \
rd=usbroot0 unentitled_ios_sim_launch=1 ignition_level=1 wdt_test=no_user_checkin \
ufsrw=1 rootrw=1 launchd_unsecure_cache=1 wdt=-1 rosemaryfb_hz=30 \
rosemarytouch=0 rosemarykeys=0
```

`rd=usbroot0` заработает только после этапа 4 (драйвер в ядре). До этого
`rd=usbroot0` даст панику `IOFindBSDRoot: ... unavailable` — это ожидаемо и
является проверкой, что ветка вообще сработала.

## 7. Результат первого прогона (2026-11-04) и точная причина нулей

Прогон `shim-usbdiag.img` (stage 1) с кабелем к ПК дал по DWC3 **все нули**
(`gsnpsid=0`, `caplen=0`, `gctl=0`), при этом IPPC и U3PHY ответили:
`ippc0=10411021`, `ippc4=1`, `ippc8=1`, `u3phy0=1E1E1900`.

Расшифровка по `mtu3_hw_regs.h` (IPPC):

| регистр | значение | смысл |
|---|---|---|
| `PW_CTRL0` (+0x00) | `0x10411021`, bit0=1 | `SSUSB_IP_SW_RST` — **весь IP в программном сбросе** |
| `PW_CTRL1` (+0x04) | `1`, bit0=1 | `SSUSB_IP_HOST_PDN` — **host-домен выключен** |
| `PW_CTRL2` (+0x08) | `1` | device-домен тоже выключен (LK закончил fastboot) |
| `PW_CTRL3` (+0x0c) | `1` | PCIe-домен выключен |

То есть контроллер не «мёртв» и не потерян по адресу — LK оставил его в
reset + host-powered-down. Это и объясняет нули во всех регистрах ядра
(`GSNPSID` — константа, но в сбросе читается как 0).

Правильная последовательность (по вендорскому драйверу `mtu3_host.c`):

```
1. клоки:   INFRA_AO +0xa4 |= bit1  ("infra_usb", usb_top_sel)
                            |= bit31 ("infra_ssusb_xhci")
            INFRA_AO +0x80 |= bit8  ("infra_icusb")
2. 26 МГц:  APMIXED +0x20 clear bit4 ("apmixed_ssusb26m", инверсный гейт)
3. IPPC +0x00: bit0 = 0   (снять SSUSB_IP_SW_RST)
4. IPPC +0x04: bit0 = 0   (снять SSUSB_IP_HOST_PDN)
5. IPPC +0x50: PDN=0, DIS=0, HOST_SEL=1   (U2 порт 0 в host)
6. ждать IPPC +0x10: bit0 SYSPLL_STABLE, bit8 REF_RST_B,
         bit10 SYS125_RST_B, bit11 XHCI_RST_B;  +0x14 bit0 U2_MAC_RST_B
7. только теперь GSNPSID != 0, PORTSC.PP=1, ждать CCS
```

Ожидаемые значения `PW_STS1` при живых клоках: `0x00000D01`
(bits 0, 8, 10, 11) и `PW_STS2 = 0x00000001`.

Это и есть содержание stage 2 (`shim/usb.c`, `usb_probe(2)`). VBUS по-прежнему
не включается: для CCS нужен питаемый хаб или флешка через OTG с внешним
питанием.

## 7.1 Второй прогон (stage 2, 2026-11-05): гейты включились, клока всё ещё нет

Оба лога (с кабелем к ПК и с флешкой) **идентичны** — что логично, порт ещё не
инициализирован. Итог прогона:

- `infra2_sta = 80000002` — гейты `infra_usb` (bit1) и `infra_ssusb_xhci` (bit31)
  в INFRA_AO реально включились;
- но `pw_sts1 = 00000000`, `pw_sts2 = 00000000`, `gsnpsid = 0` — **клок до ядра
  не доходит**;
- и аномалия: после наших записей `pw_ctl0` читается как `0`, хотя в stage 0
  он был `0x10411021`. Значит одна из записей того прогона сбросила/расшевелила
  сам блок IPPC. Кандидат — запись в `APMIXED+0x20` (гейт 26 МГц).

Не хватает верхнего слоя дерева клоков (TOPCKGEN), которого я в stage 2 не трогал:

| мукс (CK_CFG_8 @ 0x100000a0) | биты | родители |
|---|---|---|
| `usb_top_sel` | [9:8] | clk26m, univpll_d5_d4, univpll_d3_d4, univpll_d5_d2 |
| `ssusb_top_xhci_sel` | [17:16] | те же |

Фиксация выбора — `CK_CFG_UPDATE1` (0x10000008), биты 1 и 2. PLL: `univ2pll`,
бит включения — `APMIXED+0x24C` bit0 (`APMIXED+0x240/0x244` — CON0/CON1).

Поэтому **stage 3** (`usb_probe(3)`) сделан как бисект с чтением после каждой
записи: снимок всех регистров → INFRA2 → INFRA0 → IPPC → мукс на **clk26m**
(без PLL) → мукс на **univpll_d5_d4**. По какому из двух вариантов `pw_sts1`
оживёт и `gsnpsid` станет ненулевым и понятно, что программировать дальше.
`APMIXED` в stage 3 **не пишется вообще**: PLL вслепую не включаем.

Ожидаемые значения при живых клоках: `pw_sts1 = 0x00000D01`
(bits 0 SYSPLL_STABLE, 8 REF_RST_B, 10 SYS125_RST_B, 11 XHCI_RST_B),
`pw_sts2 = 0x00000001`, `caplen = 0x40`, `gsnpsid = 0x5533xxxx`.

## 7.2 Третий прогон (stage 3, 2026-11-05): муксы и PLL ни при чём

Логи с кабелем и с флешкой опять идентичны. Разбор:

| строка | вывод |
|---|---|
| `top_cfg8=02030300` | до наших записей оба мукса (`usb_top_sel`, `ssusb_top_xhci_sel`) стояли на родителе **3** = `univpll_d5_d2` — это выбор LK |
| `infra2_sta=80000002` (после записи) | гейты `infra_usb` + `infra_ssusb_xhci` включились |
| `pw_ctl0` стал `0` ровно после этой записи | пока гейт закрыт, IPPC читается мусором (`0x10411021`); после открытия — реальные значения. То есть запись в INFRA реально работает |
| `top_cfg8=02000000` | мукс на `clk26m` (без PLL) — записался |
| `univ_pwr` 0x80000000 → 0x80000001 | при выборе univpll TOP-контроллер действительно запрашивает питание PLL |
| `sts1=0 sts2=0` во всех вариантах | внутренние reset-сигналы USB-IP всё равно ассертированы |

DT закрывает вопрос о полноте списка клоков: у `mtu3_0@11200000` всего **два**
клока — `infracfg_ao` id 91 (`infra_usb`) и id 105 (`infra_ssusb_xhci`), т.е. ровно
те два гейта, что мы включили. Третьего скрытого гейта нет.

Вывод: дело не в муксе и не в PLL, а в **PHY и порядке инициализации**. В
вендорском драйвере порядок такой:

```
клоки -> VUSB10_ON + выход из UART-mode (PHY) -> phy_power_on
      -> ssusb_ip_sw_reset -> host_enable (HOST_PDN=0, U2 host_sel) -> check clocks
```

Мы делали `ip_sw_reset` и `host_enable`, **ни разу не включив PHY** — поэтому
`pw_sts1` и стоит в нулях.

### Stage 4 (`usb_probe(4)`): PHY-подмножество + тот же порядок

Раскладка `MT_PHY_V2` (из `phy-mtk-mt6785.c`):

```
U2/common блок   = 0x11e40300   (U2PHYACR4 +0x20, USBPHYACR6 +0x18,
                                 U2PHYDTM0 +0x68, U2PHYDTM1 +0x6c)
U3PHYA блок      = 0x11e40b00   (PHYA_REG1 +0x04)
```

Записывается (минимум из `phy_init_soc`):

| регистр | что |
|---|---|
| PHYA_REG1 | bit29 `VUSB10_ON` = 1 |
| U2PHYDTM0 | очистить UART_MODE[31:30], FORCE_UART_EN[26], FORCE_SUSPENDM[18] |
| U2PHYDTM1 | очистить RG_UART_EN[16] |
| U2PHYACR4 | очистить GPIO_CTL[9], GPIO_MODE[8], DP_100K_EN[16], DM_100K_EN[17]; выставить DP_100K_MODE[18] |
| USBPHYACR6 | очистить BC1.1_SW_EN[23], OTG_VBUSCMP_EN[20] |

Затем: `IPPC` импульс `sw_rst` → `HOST_PDN=0` → `U2_CTRL host_sel=1` → мукс назад
на родителя 3 → ждать `sts` → читать `GSNPSID` → `PORTSC.PP` + `CCS`.

Что осталось за кадром (и может понадобиться дальше): полный
`phy_init_soc`/`phy_recover` с efuse-триммингом и slew-rate калибровкой,
`U3D_SSUSB_REF_CK_CTRL` (IPPC+0x8C, его не пишет никто из вендорского PHY-кода),
и `vusb33` — LDO `ldo_vusb` PMIC (MT6359), для которой из шима нужен pwrap-доступ
(в XNU он уже есть: `rosemary_pwrap_write16`).

## 7.3 Четвёртый прогон (stage 4, 2026-11-05): PHY живой, IP — нет

Оба лога одинаковые. Разбор:

| строка | вывод |
|---|---|
| `phya1=60000007` до и после записи | бит 29 (`VUSB10_ON`) уже был установлен → USB2 PHY по 1.0 В **уже питается** |
| `u2dtm0=02000000` | UART_MODE[31:30], FORCE_UART_EN[26], FORCE_SUSPENDM[18] были уже сняты LK |
| `u2acr4=0004001A` после нашей записи | бит18 `DP_100K_MODE` реально встал → **регистры PHY пишутся** (банк PHY `0x11e40300` жив и тактируется) |
| `sts1/sts2=0`, `gsnpsid=0` | а вот SSUSB IP (IPPC + DWC3 core) отдаёт нули |

Итог: питание PHY и доступ к PHY-регистрам есть, клоки по DT включены, мукс рабочий — но
сам IP как будто в reset/без клока. Две оставшиеся версии:

1. блок SSUSB удерживается в reset чем-то вне IPPC (тогда все его регистры читаются нулём);
2. **перевёрнутая полярность гейтов** INFRA2 bit1/bit31: наши «enable» на самом деле выключают
   USB-клок (тогда объясняется и аномалия «`pw_ctl0` был `0x10411021`, после включения гейтов стал 0»:
   блок был живой до нашей записи).

### Stage 5 (`usb_probe(5)`): проверка «а блок-то живой?»

Самый надёжный признак — **аппаратные константы** IPPC `HW_ID` (0xA0) и `HW_SUB_ID` (0xA4):
они не могут быть нулём в живом блоке. Плюс capability-регистры `XHCI_CAP`/`DEV_CAP`,
`REF_CK_CTRL` и `DEV_RST_CTRL`.

Сценарий (каждый шаг с печатью):

```
A) как оставил LK, без записей  -> hw_id, caps, ctl0, sts1, gsnpsid
   + снимок reset-банков INFRA_AO 0x120/0x124/0x128/0x130/0x138/0x148
B) CLR infra2 bits 1,31          -> те же регистры
C) SET infra2 bits 1,31          -> те же регистры
D) IPPC write/readback (sw_rst)
E) DWC3 write/readback (GCTL.PrtCapDir = 10b)
```

Что получим:

- `hw_id != 0` только в B (или только в C) → узнаём правильную полярность гейтов
  и что IP живой — это сразу закрывает дыру;
- `hw_id == 0` везде → блок в reset/за доступом: смотрим `rst*_sta`, ищем ассертнутый
  бит SSUSB/USBSIF и снимаем его;
- D/E показывают, пишутся ли IPPC и DWC3 вообще.

## 7.4 Пятый прогон (stage 5, 2026-11-05): ПОЛЯРНОСТЬ ГЕЙТОВ ПЕРЕВЁРНУТА, а IP — в reset

Прогон с тремя состояниями дал однозначный ответ:

| состояние | `hw_id` | `ctl0` | `u2_ctrl0` |
|---|---|---|---|
| A) как оставил LK, без записей | `20170717` | `10411021` | `0000004F` |
| B) после записи в **CLR** (0xa8) bits 1,31 | `20170717` | `10411021` | `0000004F` |
| C) после записи в **SET** (0xa4) bits 1,31 | **0** | **0** | **0** |

Вывод: бит в этих регистрах = **1 означает «клок выключен»** (активно-низкие гейты).
Запись в SET (то, что я делал в stage 2..4) USB-клок **выключала**, поэтому все
регистры потом читались нулём и любые записи в IPPC/DWC3 падали.

Второе, главное. В живом состоянии (A):

```
ctl0 = 0x10411021  -> bit0 = 1  = SSUSB_IP_SW_RST ассертнут (IP в reset)
ctl1 = 0x00000001  -> bit0 = 1  = SSUSB_IP_HOST_PDN (host выключен)
u2_ctrl0 = 0x4F    -> bits0,1 = 1 = U2 port DIS + PDN
ref_ck_ctrl = 0x1F, dev_rst_ctrl = 0x00 (dev reset не ассертнут)
xhci_cap = 0x100, dev_cap = 0x101, hw_id = 0x20170717
```

То есть блок жив и читается, но LK оставил его в **программном reset** с выключенным
host-доменом и выключенным U2-портом. Именно поэтому `GSNPSID` (аппаратная
константа) читался как 0.

### Stage 6 (`usb_probe(6)`): правильная последовательность

```
B) CLR infra2 bits 1,31 (+ infra0 bit 8)  -- клок ВКЛЮЧИТЬ (активно-низкий гейт)
C) ctl0 &= ~bit0                          -- снять SSUSB_IP_SW_RST
D) ctl1 &= ~bit0                          -- включить host-домен
E) u2_ctrl0 & ~(DIS|PDN) | HOST_SEL       -- поднять порт 0 в host
F) ждать sts1/sts2, читать GSNPSID/caplen/GCTL/DSTS
G) PORTSC.PP=1 -> опрос CCS
```

Ожидаем: `gsnpsid=5533xxxx`, `caplen=0x40`, `sts1` с битами 0/8/10/11.

## 7.5 Шестой прогон (stage 6, 2026-11-05): КОНТРОЛЛЕР ЖИВОЙ

Правильная последовательность сработала полностью:

| шаг | результат |
|---|---|
| `CLR infra2 1,31` | `hw_id=20170717` — клок есть, блок читается |
| `ctl0 &= ~SW_RST` | `ctl0=10411020`, запись **легла** (до этого блок был unclocked и записи падали) |
| `ctl1 &= ~HOST_PDN` | `ctl1=00000000` |
| `u2_ctrl0` | `0000004C` — DIS/PDN сняты, HOST_SEL стоит |
| ожидание клоков | **`sts1=0x3D0F`, `sts2=1`, `ok=1`** — SYSPLL/REF/SYS125/XHCI reset-B поднялись |
| xHCI | **`caplen=0x20`** — capability-регистры читаются |

Осталось два открытых пункта:

1. `gsnpsid`/`gctl`/`dsts` (по адресам 0xc120/0xc110/0xc70c) всё ещё 0 — значит блок
   global/device у этого ядра лежит не там (или требует отдельного клока). Надо найти
   его смещение/блок.
2. `usbcmd=0` — контроллер **стоит** (`Run/Stop=0`), поэтому порт в PLS=14 и
   `CCS=0`. Нужно запустить xHCI и дать VBUS.

### Stage 7 (`usb_probe(7)`)

```
0) повтор рабочего power-сценария
1) xHCI caps: caplen, HCSPARAMS1, +08..+1c
2) dump DWC3 global @1120c100   - ищем 5533xxxx (GSNPSID)
3) dump MTK MAC glue @11201000 - альтернативное место global/device regs
4) op base = 11200000+caplen: USBCMD / USBSTS / PORTSC
5) USBCMD.RS=1 -> ждём, читаем USBSTS
6) PORTSC: PP=1 + три выборки (PP, PLS, CCS)
```

Про VBUS: чтобы увидеть `CCS=1` (и потом пойти в enumeration), нужен либо
питаемый USB-хаб (его upstream-порт поднимает pull-up от своего питания),
либо включение OTG-boost на MT6360 через PMIC/pwrap — это следующий кусок работы.

## 7.6 Седьмой прогон (stage 7, 2026-11-05): xHCI запускается

| строка | разбор |
|---|---|
| `caplen=0x20` | область capability 32 байта — валидно |
| `+10=01400F99` (HCCPARAMS1) | AC64=1, **PPC=1** (управление питанием порта есть), MaxPSASize=15, XECP=0x140 |
| `+14=00000800`, `+18=00000600` | DBOFF=0x800, RTSOFF=0x600 → doorbell `0x11200800`, runtime `0x11200600` |
| `usbcmd=0`, `usbsts=1` до старта | HCH=1 — контроллер остановлен |
| после `RS=1`: `usbcmd=1`, `usbsts=0` | **контроллер запустился**, HCH снят |
| `portsc=000003C0` | PP=1, PLS=14, CCS=0 — порт включён, но линия не «увидела» сессию |
| dump `1120c100` и `11201000` | нули — DWC3 global/MAC регистры по этим адресам недоступны |

Последнее не критично: для работы с устройством достаточно стандартного xHCI
(CRCR/DCBAAP/ERST/DBOFF — всё читается). `GSNPSID` — просто красивая строчка.

Остаётся **PHY/session**: PLS=14 — не «RxDetect», значит PHY считает сессию
невалидной. MTK для этого использует флаги в `U2_CTRL0`: `FORCE_IDDIG` (bit11,
принудительно A-device/host) и `VBUSVALID` (bit9, «сессия есть»).

### Stage 8 (`usb_probe(8)`)

```
0) power seq (CLR гейтов, снять SW_RST, host on, U2 port up)
1) HCRST (USBCMD bit1), ждать снятия
2) CNR wait + USBCMD.RS=1
3) A: PP=1                -> portsc/pls
4) B: + FORCE_IDDIG       -> portsc/pls   (бисект по флагам)
5) C: + VBUSVALID         -> portsc/pls
6) ещё 5 выборок за 500 мс
```

Ожидаем: PLS перейдёт в 5 (RxDetect); с питаемым хабом на линии — 7 (Polling),
`CCS=1`, и в разрядах скорости [13:10] появится значение (1=LS, 2=FS, 3=HS).

## 7.7 Восьмой прогон (stage 8, 2026-11-05): xHCI работает, порт — нет

| строка | вывод |
|---|---|
| HCRST → `usbcmd=0`, `usbsts=1` | сброс принят, HCH выставлен |
| `RS=1` → `usbcmd=1`, `usbsts=0` | контроллер идёт |
| `u2_ctrl0` `0x84C` → `0xA4C` | записи в IPPC ложатся (FORCE_IDDIG/VBUSVALID установились) |
| `portsc=000003C0` во **всех** состояниях | PP есть (bit9), но PLS=14 (нестандартно), CCS=0, PED=0 — значение «заморожено» |

Настоящий host-порт с PP=1 и RS=1 обязан показывать минимум PLS=5 (RxDetect).
То, что значение не меняется совсем, означает: **вероятно, мы читаем
PORTSC не по той базе операционных регистров**. Два кандидата: `caplen = 0x20`
(как читается байт 0) и `0x40` (типично для DWC3). Оба и проверяются.

### Stage 9 (`usb_probe(9)`)

```
0) power seq (сразу с FORCE_IDDIG + VBUSVALID)
1) HCSPARAMS1 (MaxPorts), IPPC OTG_STS (VBUS_VALID), ref_ck_ctrl,
   extended caps @0x140
2) HCRST+RS на op=0x20 -> PP-проба: какой из баз реально ловит PP
3) HCRST+RS на op=0x40 -> то же
4) PORTSC порта 0 и 1 на обеих базах
```

Отдельно важно: и `0x1120c100` (DWC3 global), и `0x11201000` (MAC glue)
читаются нулём. Это может значить, что не хватает **третьего клока** —
«mac2» из лога LK (`clk mac2:OK`). Пока он выключен, мы не можем писать
`GUSB2PHYCFG`/`DCTL`, т.е. управлять портом со стороны DWC3.

## 7.8 Девятый прогон (stage 9, 2026-11-05): база подтверждена, порт в «inactive»

| строка | вывод |
|---|---|
| `pp_sticks=00000200` на op=0x20 | **база верная**: `caplen=0x20`, op=`0x11200020`, PORTSC=`0x11200420`, PP ложится |
| op=0x40 всё нули | 0x40 — не операционная база |
| `hcs1=0100020F`, `maxports=1` | MaxSlots=15, MaxIntrs=2, **один порт** |
| `otg_sts=00000000` | `VBUS_VALID` (bit9) = 0 — IP не видит сессию. На MTK этот бит питается от charger/extcon-пути, которого здесь нет, поэтому ноль даже при физически воткнутом кабеле |
| `ref_ck_ctrl=00000001` | после релиза reset из `0x1F` стало `0x01` — ref-клок включён |
| `xecp140=0` | расширенные capability пустые (мелочь) |
| `pls=14` навсегда | порт так и не входит в RxDetect |

То есть опрос идёт по правильному адресу, контроллер работает, но порт
удерживается в нестандартном состоянии 14. В `u2_ctrl0` (0x4C, как оставил LK)
есть недокументированные в заголовке биты 3 и 6 — их и проверяем бисектом.

### Stage 10 (`usb_probe(10)`)

```
0) power seq, HCRST+RS, PP=1  -> portsc/pls
1) bisect u2_ctrl0: 0x04 (только host_sel) -> 0x0C (+bit3) -> 0x44 (+bit6)
                    -> 0x4C (как LK) -> +force_iddig -> +vbusvalid -> обратно 0x04
   после каждого — portsc/pls/otg_sts
2) PHY: UTMI_MUXSEL(bit15) + clear FORCE_SUSPENDM + FORCE_DRVVBUS(bit24)
   -> повторная проба порта
```

Цель — увидеть `pls=5` (RxDetect). После этого с питаемым хабом на линии
должно появиться 7 (Polling) и `ccs=1`, и можно писать enumeration.

## 7.9 Десятый прогон (stage 10, 2026-11-05): порт ждёт сигналов сессии от PHY

Бисект `u2_ctrl0` (0x04 → 0x0C → 0x44 → 0x4C → +IDDIG → +VBUSVALID → назад)
дал **ровно одно значение**: `portsc=000003C0`, `pls=14`, `otg_sts=0` — ни в одной
комбинации ничего не меняется. Даже `UTMI_MUXSEL` + `FORCE_DRVVBUS` в PHY
(`dtm0` из `0x02000000` стал `0x03008000`) не сдвинули ни бита.

Значит порт держится не битами IPPC, а **сигналами сессии от PHY**:
`U2PHYDTM1` был `0x00000000`, т.е. PHY не сообщает ни VBUSVALID, ни AVALID —
именно поэтому `otg_sts.VBUS_VALID=0` и PLS не уходит из 14.

### Что я нашёл в вендорском `phy_recover()` (`phy-mtk-mt6785.c`)

После включения питания PHY он пишет — и мы этого не делали ни разу:

```
U2PHYDTM1: RG_VBUSVALID=1 (bit5), RG_AVALID=1 (bit2), RG_SESSEND=0 (bit4)
USBPHYACR6: RG_USB20_DISCTH = 0xF (bits 7:4)
U2PHYDTM0: снять RG_DPPULLDOWN/DMPULLDOWN/XCVRSEL/TERMSEL/DATAIN
           и все FORCE_* того же набора
```

То есть PHY только тогда говорит контроллеру «A-девайс, сессия валидна».
ВTalkже важно: `UTMI_MUXSEL` вендор не ставит — в stage 11 я его снимаю.

### Stage 11 (`usb_probe(11)`)

Вендорский порядок `phy_recover` → `u2_ctrl0=host_sel` → HCRST/RS/PP → проба
порта дважды (с host_sel и с `+VBUSVALID+IDDIG`).

Ожидаем: `dtm1=00000024`, `otg_sts` bit9 = 1, `pls=5` (RxDetect).
С питаемым хабом на линии — `pls=7` и `ccs=1`.

Если и это не сдвинет — остаются два непочатых куска вендорского init:
`phy_efuse_settings()` (efuse-тримминг) и `phy_slew_rate_calibration()` (ADC),
а также реальный VBUS через MT6360.

## 7.10 Прогоны 13–14 (2026-11-05): всё готово, кроме 5 В на VBUS

Stage 13 прогнан трижды: с кабелем к ПК, с флешкой напрямую, с питаемым хабом
через переходник A→C. **Все три лога идентичны:**

```
op=11200020 hcs1=0100020F db=11200800 rt=11200600
pagesize=00000001 maxslots=0000000F
HCRST -> cmd=00000000 cnr=00000000
ps=00000?A0 pls=00000005 ccs=00000000 spd=00000000
no device on the port (VBUS?)
```

Что это подтверждает: xHCI полностью функционален (база, doorbell, runtime,
pagesize, слоты, сброс), порт в RxDetect (`pls=5`), и единственное, чего не хватает
— **5 В на VBUS**. Хаб не помогает, потому что хаб не подаёт VBUS вверх по
upstream-порту, а переходник A→C только коммутирует линии и ничего не питает.

### Два пути к VBUS

1. **Y-кабель «USB-C OTG + зарядка»** + обычная 5 В зарядка — рекомендуемый:
   штатный режим, PMIC не трогаем.
2. **Софт: OTG-boost на MT6360** — нужен I2C-мастер в шиме (MT6360 в нашем DTB
   не висит ни на одной i2c-шине) и регистры charger. Рискованнее (PMIC).

### Stage 14 (`usb_probe(14)`)

Ждёт появления устройства до 5 с, затем: Enable Slot → Address Device →
GET_DESCRIPTOR(device 18) → GET_DESCRIPTOR(config, сначала 9 байт, потом
wTotalLength) → разбор дескрипторов → вывод VID/PID, класса, bulk-эндпоинтов
(`ep_in`, `ep_out`, `mps_in`, `mps_out`, `cfgval`).

С Y-кабелем один прогон должен дать эти цифры, после чего остаётся BOT/SCSI:
CBW/CSW, INQUIRY, READ CAPACITY(10), READ(10) сектора 0 и проверка сигнатуры HFS+.

## 7.11 Прогон stage 34 (2026-11-05): вольтметр работает, boost — нет

Два прогона одного образа (md5 `ee41571e…`): (1) с флешкой USB-C без кабеля,
(2) с кабелем к ПК.

| | флешка, без питания | кабель к ПК |
|---|---|---|
| `raw0/mv0` | 0 / 0 | `0x59B` / `0x2308` = 8969 мВ |
| `raw1/mv1` | 0 / 0 | `0x31F` / **`0x1381` = 4993 мВ** |
| `raw2/mv2` | 0 / 0 | `0x31F` / 4993 мВ |
| `chg1` (CHG_CTRL1) | `0x01` (OPA_MODE держится) | `0x01` |

**Вывод 1: вольтметр живой и меряет именно VBUS на разъёме.** 4993 мВ против
эталона Android `VOLTAGE_NOW = 5037 мВ` — расхождение 0.9 % (просадка кабеля),
и это ровно та нога, куда обязан попадать boost. Значит нули в первом логе —
не артефакт измерения.

**Вывод 2: `mv0` — мусор по построению.** `ADC_RPT_1 (0x5A)` в младшем ниббле
содержит номер канала, который реально сформировал `ADC_RPT_2/3`. Вендорский
драйвер ждёт совпадения этого ниббла с запрошенным каналом (до 10 повторов).
Stage 34 читал `0x5B:0x5C` сразу, поэтому первый сэмпл — остаток предыдущей
конверсии (0x59B). Отсюда правило: **сначала проверять `0x5A & 0x0F`, потом
верить данным** (реализовано в `pmu_adc_raw()`).

**Вывод 3: boost не запускается.** При `OPA_MODE=1` и `VOBST=0x5C` (= 4425 +
23·25 = **5000 мВ**) на VBUS ровно 0. Ноль, а не «просадка»: конвертер не
коммутирует вовсе. На кабеле при том же `OPA_MODE=1` видно 4993 мВ — то есть
boost при наличии внешнего VBUS честно не включается (норма), а без него не
включается тоже (проблема).

### Что осталось непроверенным к этому моменту

- `CHG_WDT_EN` (`CHG_CTRL13 = 0x1D`, bit7): `mt6360_enable_otg()` включает
  watchdog **перед** `OPA_MODE`; stage 34 этого не делал.
- **Фронт `OPA_MODE`.** Бит живёт в PMIC и переживает reset SoC. Если он уже 1
  (после предыдущего прогона), запись `c11 |= 1` не даёт перехода 0→1 — FSM
  может просто не увидеть команду. Нужен явный спад и фронт.
- `VIN_OVP` (`CHG_CTRL19 = 0x61`, биты [6:5]: 5.5 / 6.5 / 10.5 / 14.5 В).
  Вендорский init ставит **14.5 В**; если стоит 5.5 В, выход буста 5.0 В может
  валить компаратор OVP.
- `OTG_OC` (`CHG_CTRL10 = 0x1A`, биты [2:0]). Stage 33/34 писали `| 0x0F`,
  задевая бит 3 соседнего поля.
- Скрытые регистры charger `0x30..0x3F` (разблокировка pas-code `69 96 63 72`
  в `0x07..0x0A`) — ни разу не читались.
- Статусы `0x27 USB_STATUS1`, `0x4A CHG_STAT`, `0xE0/0xE1` — ни разу не
  читались после boost (диффом 0x00..0x1F их не видно).
- ADC `VBAT` (канал 4) / `VSYS` (канал 3) — вход буста. Если батареи нет или
  она ниже порога, boost физически не может стартовать.

### Stage 35 (`usb_probe(35)`) — ровно эти пункты

Порядок: VBAT/VSYS/VBUS → дамп `0x11/0x15/0x1A/0x1D/0x61/0x27/0x4A/0xE0/0xE1`
→ C1 watchdog + чистый фронт `OPA_MODE` (VOBST 5.00 В) → замер → C2 `VIN_OVP`
→ 14.5 В + фронт → замер → C3 `OTG_OC` = 7 (маска `0x07`) → замер → C4
разблокировка скрытых и дамп `0x30..0x37` → C5 ещё фронт → замер + `CHG_STAT`.

Каждый кандидат меряется тем же проверенным вольтметром, так что один прогон
даёт 4 независимых ответа «да/нет», а не один.

## 7.12 Прогон stage 35 (2026-11-05): ADC не обновился, но boost, похоже, ожил

```
USBv2 vbat=00000EA8 raw=00000BBA     <- VBAT 3752 мВ
USBv2 vsys=00000EA8 raw=00000BBA     <- то же самое
USBv2 vbus0=0000494A raw=00000BBA    <- и это тоже: 18.7 В — невозможно
USBv2 c11=00000000 c15=00000067      <- charger в дефолте
USBv2 c1a=0000005B c1d=00000052
USBv2 usb27=00000000 chg4a=00000002
USBv2 c1 vbus=0000494A c11=00000001  <- C1: watchdog + фронт
USBv2 c2 vbus=0000494A c61=00000060  <- C2: VIN_OVP 14.5 В
USBv2 c3 vbus=0000137B c1a=0000005F  <- C3: OTG_OC=7  -> 4987 мВ
USBv2 h0x30=3F h31=98 h32=A1 h33=73 h34=00 h35=0F h36=5C h37=20
USBv2 fin vbus=0000137B chg4a=0000000A
```

**ADC не мерил вовсе.** Все три канала вернули **один и тот же** raw `0x0BBA`.
Физически невозможно, чтобы VBAT, VSYS и VBUS совпали: значит данные в
`0x5B:0x5C` не обновлялись, и `0x0BBA` — остаток какой-то прежней конверсии
(3002 LSB = 3752 мВ по шкале VBAT, что похоже на правду для VBAT и полностью
бессмысленно для VBUS: 18.7 В). Вывод `vbat=`/`vsys=` в этом прогоне
**недействителен**, и по нему нельзя судить о входе буста.

Что говорит `c11=0x00`, `c15=0x67`, `c1d=0x52`, `c61=0x00`: это **заводские
дефолты** MT6360. Значит PMIC между прогонами был обесточен (полное выключение),
и зарядник стартовал с чистого листа — важный факт сам по себе: boost можно
поднять из дефолтного состояния, без «наследства» Android.

Два содержательных факта:

1. `c61=0x00` → `VIN_OVP` = **5.5 В** (sel 0). Буст нацелен на 5.00 В, то есть
   работал в 10 % от порога OVP — это реальный кандидат на «мгновенный трип».
   В C2 выставлено 14.5 В, как в вендорском init.
2. `chg4a` сменился `0x02 → 0x0A` (появился бит 3) — единственное изменение
   статуса за прогон, и оно совпадает по времени с принятием `OPA_MODE`.
   FSM зарядника на команду **отреагировал**.

К концу прогона вольтметр дважды (C3 и fin, с паузой и дампом между ними) дал
`0x137B` = **4987 мВ**, что совпадает с кабельным `0x31F` = 4993 мВ. Но именно
поэтому верить нельзя: регистр `0x5B:0x5C` хранит последнюю конверсию и
переживает reset SoC, а последний раз 5 В на этом узле были в Android при
зарядке. Один LSB разницы — не доказательство.

### Stage 36 (`usb_probe(36)`): A/B/A + CCS

1. ADC-чтение переписано: снять `adc_en` (`0x56=0`), снять канал (`0x57=0`),
   затем поднять `0x56=0x80` и `0x57=1<<ch` — это фронт и на `adc_en`, и на
   канале; поллинг младшего нибла `0x5A` до 1.2 с; в лог печатается сам `0x5A`
   (`rpt=`) и конфиг `0x56/0x57/0x58`.
2. **A/B/A**: boost off → замер, on (watchdog + VOBST 5.00 + фронт) → замер,
   off → замер. Рельс, который ходит за регистром, — настоящий.
3. Rp на CC (`ROLE_CONTROL 0x1A = 0x05`), `usb_host_up()`, ожидание
   `PORTSC.CCS` до 2 с — **свидетель, не зависящий от ADC**: подключённая и
   запитанная флешка обязана дать connect.
4. Если `CCS=1` — сразу вызывается готовый `usb_stage14()` (слоты, адрес,
   дескрипторы, эндпоинты).

Образ: `shim-usbdiag-full.img`, md5 `2f808cb66720d93860bf8ab582c77a85`.

то же самое было раньше с кабелем к ПК — но тот тест ничего не доказывал: в

## 7.14 Stage 37 (`usb_probe(37)`): три свидетеля

```
USBv4 vbus=… c11=…                 <- boost по проверенной схеме
USBv4 cc_bef=… role0=…             <- TCPC 0x11 до смены роли
USBv4 cc_aft=… role1=…             <- после ROLE_CONTROL=0x05
USBv4 otg18=… xhci_cap=…           <- IPPC 0x18 / 0x24
USBv4 u2_50=… u3_30=…              <- U2/U3 port control
USBv4 dmon1=… portsc=…             <- U2PHYDMON1 + PORTSC
USBv4 psc2=… psc3=…                <- другие порты, если карта шире
USBv4 dmon1b=… portsc2=…           <- с принудительными session-сигналами
```

`U2PHYDMON1` (U3PHY + 0x300 + 0x74) — самое ценное:

| бит | смысл |
|---|---|
| 28 | `AD_USB20_BVALID` (аналоговый, реальный) |
| 27 | `USB20_IDDIG` |
| 26 | `AD_USB20_VBUSVALID` (аналоговый!) |
| 25 | `AD_USB20_SESSEND` |
| 23:22 | `USB20_LINE_STATE`: 00=SE0, 01=J (D+ высокий), 10=K |
| 21 | `USB20_HST_DISCON` |

Если флешка запитанна и её D+ подтянут, `LINE_STATE` обязан быть `01` — тогда
проблема в контроллере/порте. Если `LINE_STATE=00` при `VBUSVALID=1`, значит
D+/D- физически не доходят до PHY (мукс/redriver на плате), и софт тут ни при
чём — нужен путь через microSD или внешний хаб с UART-логом.

`TCPC 0x11` отвечает на второй вопрос: видит ли чип флешку на CC. `00` —
не видит (проблема в Rp/CC), `10` — видит Rd (флешка подключена и запитана).

## 7.15 Прогон stage 37 (2026-11-05): найдена причина всех «портов-мертвецов»

```
USBv4 vbus=0000137B c11=00000001
USBv4 cc_bef=00000002 role0=0000000A     <- CC1=Rd: флешка видна ещё до смены роли
USBv4 cc_aft=00000002 role1=00000005     <- мы Rp/Rp, флешка на CC1 Rd
USBv4 otg18=00000000 xhci_cap=00000100   <- IPPC OTG_STS=0; 1 U2-порт, 0 U3-портов
USBv4 u2_50=0000004F u3_30=0000020F
USBv4 dmon1=2A400000 portsc=000002A0     <- до форса: PLS=5, CCS=0
USBv4 dmon1b=2A400000 portsc2=000202E1   <- после форса: CCS=1, CSC=1, PLS=7 (Polling)
USBv4 device seen: enumerating
```

**`dmon1=0x2A400000` — это и есть объяснение.**

| бит | значение | смысл |
|---|---|---|
| 26 | **0** | аналоговый `VBUSVALID` = 0 (а на разъёме 4.99 В!) |
| 25 | **1** | `SESSEND` = 1 — PHY считает, что сессии нет |
| 27 | 1 | `IDDIG` = 1 (аналоговый ID «как у устройства») |
| 23:22 | `01` | `LINE_STATE` = **J** — D+ подтянут, флешка жива и запитана |
| 21 | 0 | `HST_DISCON` = 0 |

То есть: флешка всё это время была подключена и подавала J на D+, а PHY **не
видел ни VBUS, ни сессии** — потому что на этой плате `VBUSVALID`/`SESSEND`
U2-PHY не подключены к VBUS разъёма (это подтверждает и `IPPC OTG_STS=0`).
Контроллер честно сидел в RxDetect и «не видел» устройство.

Лечение — принудительные session-сигналы UTMI:
```c
wr32(PHY_U2PHYDTM1, FORCE_VBUSVALID | FORCE_SESSEND | FORCE_AVALID |
                     RG_VBUSVALID | RG_AVALID);   /* 0x2614 */
```
После этого `PLS 5 -> 7` (Polling), `CCS 1`, `CSC 1`. Это ответ на вопрос
«почему не виделся даже кабель к ПК» — не виделся бы и увиден: дело было не в
VBUS и не в D+/D-, а в двух аналоговых входах PHY.

Ещё из этого лога: `xhci_cap=0x100` → **1 U2-порт и 0 U3-портов**. SS-пары
коннектора к этому контроллеру не заведены, значит флешка USB 3.0 обязана
падать на USB2 — это нормально и ожидаемо.

## 7.16 Stage 38 (`usb_probe(38)`): сброс порта и исправленная адресация

Прогон stage 37 дошёл до `enslot=00000005` (TRB Error) и встал. В коде
enumeration нашлись три ошибки:

1. **`CONFIG.MaxSlotsEn` = 15 при `MaxSlots = 1`** (`HCSPARAMS1 = 0x0100020F`,
   старший байт — это MaxSlots). Включение большего числа слотов, чем есть,
   валит Enable Slot.
2. **Add-флаги Input Control Context писались в dword 0.** В xHCI dword 0 ICC —
   это **Drop** Context Flags, dword 1 — Add. `x_inctx[0] = 3` просил
   *выкинуть* контексты A0/A1 вместо того, чтобы их добавить.
3. **Не было сброса порта.** После детекта устройство остаётся в состоянии
   Default, а порт — в Polling; без `PORTSC.PR` ни Enable Slot, ни Address
   Device не имеют смысла.

Stage 38 = boost (проверенная схема) + `ROLE_CONTROL=0x05` + форс сессии +
`usb_stage14()` с порт-ресетом. Ожидаемый лог: `rst ps=…` (PED=1, PLS=0,
spd=3), затем `enslot=1`, `addr=1`, `devdesc=1`, `vid_pid`, `ep_in/ep_out`.

## 7.17 Прогон stage 38 (2026-11-05): порт сброшен, найдены 3 ошибки в xHCI-коде

```
USBv5 vbus=0000137B c11=00000001
USBv5 role=00000005
USBe  pagesize=00000001 maxslots=0000000F   <- на самом деле это MaxPorts!
USBe  ps=000202E1 pls=00000007              <- Polling
USBe  ccs=00000001 spd=00000000
USBe  rst ps=00000E03 pls=00000000          <- reset ok: PED=1, PLS=0 (U0)
USBe  ped=00000002 spd=00000003             <- High Speed
USBe  enslot=00000005 slot=00000001         <- всё ещё TRB Error
```

Сброс порта отработал ровно как надо: `PLS 7 -> 0` (U0), `PED=1`,
`speed=3` (High Speed). То есть физически коннект есть и порт обучен.

**`enslot=5` (TRB Error) — это не порт, а наш xHCI-код. Три ошибки:**

1. **Смещения регистров колец были сдвинуты.** `op` = `DWC3_BASE + caplength()`
   = `0x11200020`, а писали:
   | что | писали | правильно |
   |---|---|---|
   | CRCR (64 бит) | `op + 0x14` (**старшая** половина CRCR) | `op + 0x10` |
   | DCBAAP (64 бит) | `op + 0x20` (это **CONFIG**!) | `op + 0x18` |
   | CONFIG | `op + 0x28` (зарезервировано) | `op + 0x20` |
   Итог: **CRCR = 0**, контроллер шёл за командным TRB по физическому адресу 0
   и возвращал «TRB Error» (код 5), а DCBAA тоже оставался нулевым.
2. **Slot ID в TRB лежит в битах [31:24], тип — в [15:10].** Address Device
   вызывался как `type = (11 << 10) | slot`, внутри ещё раз `<< 10` — в поле
   типа попадал номер слота (1 = Normal TRB), а Slot ID = 0. В control-трансферных
   TRB (`xhci_ctrl_in`) Slot ID не заполнялся вообще, а у Data/Status Stage были
   перепутаны биты DIR (`bit16`).
3. **DCBAA — массив 64-битных указателей**, а писали `x_dcbaa[x_slot]` вместо
   `x_dcbaa[2 * x_slot]`.

Всё это исправлено; stage 38 теперь вызывает тот же `usb_stage14()` с правильным
командным кольцом. Если `enslot=1`, дальше должны пойти `addr=1`,
`devdesc=1 vid_pid=…`, `cfg9/cfglen`, `ep_in/ep_out`, `mps_in/mps_out`.

### Stage 39 (`usb_probe(39)`): readback и сырое событие

Печатает:
1. `op=`, `hcsp1=`, `hccp1=`, `db_rt=` — карта capability-блоков;
2. `cmd=`/`sts=` после HCRST — реально ли контроллер остановился (`HCH`);
3. `crcr=` и `want=` — **приняла ли запись CRCR** (главный вопрос), плюс
   `crcr_hi=`, `dcbaap=`, `cmd2=`/`sts2=` после старта и `config=`;
4. один Enable Slot TRB, отправленный вручную, и **дамп всех четырёх dword'ов
   события** (`ev0..ev3`, `code=`, `type=`, `slot=`).

Развилка:

| Лог | Вывод |
|---|---|
| `crcr` ≠ `want` | запись CRCR игнорируется: контроллер не остановлен / другой offset / нужен `GCTL.PRTCAP` (блок `0xc1xx` мёртв) |
| `crcr == want`, `code=5` | кольцо записано, но контроллер отвергает команду → смотреть `type=`/`slot=` и `sts2` (HSE/CNR) |
| `crcr == want`, `code=1` | команда прошла — тогда виноваты были только поля TRB |

## 7.19 Прогон stage 39 (2026-11-05): кольцо не принимается

```
USBv6 op=11200020 hcsp1=0100020F
USBv6 hccp1=01400F99 db_rt=06000800
USBv6 cmd=00000000 sts=00000001     <- после HCRST: halted, HCH=1
USBv6 crcr=00000000 want=400AB3C1   <- запись НЕ принята
USBv6 crcr_hi=00000000 dcbaap=00000000
USBv6 cmd2=00000001 sts2=00000000   <- после RS: RS=1, HCH=0 (запустился)
USBv6 config=00000000 porte=000001C0
USBv6 ev0=400AB4C0 ev1=00000000
USBv6 ev2=05000000 ev3=00008401
USBv6 code=00000005 type=00000021 slot=00000001
```

Разбор:

- **USBCMD/USBSTS (op+0x00/0x04) работают**: HCRST даёт `cmd=0, sts=1`
  (HCHalted), запись `RS=1` — `cmd2=1, sts2=0`. База `op=0x11200020` верна.
- **CRCR/DCBAAP/CONFIG читаются нулями** после записи — то есть либо запись
  игнорируется, либо читается другой регистр.
- **Решающая улика:** `ev0 = 0x400AB4C0` — это в точности адрес `x_dcbaa`
  (по символам ELF: `x_cmd = 0x2b3c0`, `x_dcbaa = 0x2b4c0`, образ грузится на
  `0x40080000`). То есть контроллер взял как указатель командного кольца
  **значение, которое мы записали в DCBAAP (`op+0x18`)**. Событие —
  `type=33` (Command Completion), `code=5` (TRB Error), цикл 1.

Значит для этого контроллера (по крайней мере по адресу записи) CRCR ведёт себя
как регистр по `op+0x18`, а не `op+0x10`. Плюс `HCCPARAMS1 = 0x01400F99` даёт
`CSZ = 0b10` (значение, зарезервированное спецификацией xHCI), а `PORTSC`
после HCRST читается как `0x1C0` — `PLS = 14`, тоже недопустимое значение.
Похоже, что capability/op-блок отвечает не совсем по стандарту.

### Stage 40 (`usb_probe(40)`): карта регистров

Не требует ни boost, ни флешки — чистый тест регистров, ~2 с. Пишет три разных
шаблона (`0x11111111` в `op+0x10`, `0x22222222` в `op+0x18`, `0x33333333` в
`op+0x20`), затем печатает дамп `op+0x00 … op+0x3C`, и отдельно — `crcrP=`
(сразу после записи CRCR, до старта) и `crcrQ=` (после RS).

| Что видно | Вывод |
|---|---|
| `10=11111111`, `18=22222222`, `20=33333333` | записи и чтения работают; значит нули в stage 39 — следствие старта/порядка |
| `10=00000000`, `18=11111111` | запись съезжает на **+8**: реальные CRCR/DCBAAP/CONFIG = `0x18/0x20/0x28` |
| всё нули | регистры `0x10..0x20` вообще не поддерживаются — это не полноценный xHCI |
| `crcrP != crcrQ` | старт контроллера стирает CRCR — нужен другой порядок инициализации |

## 7.20 Прогон stage 40 (2026-11-05): CNR — вот почему записи не доходят

```
USBv7 op=11200020 caplen=00000020
USBv7 cmd0=00000000 sts0=00000B01
USBv7 00=00000000 04=00000B01
USBv7 08=00000001 0c=00000000
USBv7 10=00000000 14=00000000 ... 3c=00000000   <- всё 0
USBv7 crcrP=00000000 want=400AB3C1
USBv7 crcrQ=00000000 dcbap=00000000
USBv7 conf=00000000 sts=00000B00
```

`USBSTS = 0x0B01`: бит 0 `HCH`=1 (остановлен), биты 8/9, и **бит 11 `CNR`
(Controller Not Ready) = 1**. По спецификации xHCI, пока `CNR=1`, программное
обеспечение не должно писать в операционные регистры — и контроллер обязан
игнорировать такие записи. Ровно это и наблюдалось: `CRCR`, `DCBAAP`, `CONFIG`
и даже шаблоны `0x11111111/0x22222222/0x33333333` не осели нигде, все чтения
`op+0x10..0x3c` вернули 0. `caplen=0x20` и `PAGESIZE=1` при этом читаются
корректно — то есть база `op=0x11200020` верна, а «мёртвая» зона начинается
ровно с `0x10`.

**Почему CNR не снимается:** ядру не хватает собственной опорной частоты.
На MT6785 гейт `APMIXED_SSUSB26M` живёт в `APMIXED + 0x20`, бит 4, и он
**инверсный** (`bit = 1` → клок выключен; включается записью `1<<4` в
clear-регистр). Именно этот гейт когда-то «сломал» IPPC при слепой записи.
То же объясняет `GSNPSID = 0`: блок ядра `0x1120c100` не клокнут, поэтому
DWC3 не может завершить внутреннюю инициализацию и не снимает `CNR`.

### Stage 41 (`usb_probe(41)`)

1. читает `APMIXED 0x20` и `GSNPSID` до/после точечной записи `0x10`
   (включение `SSUSB26M`);
2. включает обычные гейты INFRA и снимает `IP_SW_RST`/`HOST_PDN`;
3. делает HCRST и **ждёт сброса `CNR`** до 1 с (`cnr_wait=` — номер итерации,
   `FFFFFFFF` = не снялся);
4. заводит кольца **с Link TRB в конце** (без него кольцо не замыкается);
5. пишет `CONFIG`/`DCBAAP`/`CRCR` и читает их обратно **до** старта (`crcrP=`),
   затем `RS` и Enable Slot.

| Лог | Вывод |
|---|---|
| `ample_aft` бит4 = 0, `gsnpsid` ≠ 0 | клок поднялся, ядро живое |
| `cnr_wait` = число | CNR снялся за N итераций — можно программировать |
| `cnr_wait` = FFFFFFFF | CNR висит: не хватает ещё одного клока/сброса |
| `crcrP == want` | кольцо принято → ждём `enslot=1` |
| `crcrP = 0` при `cnr_wait` ≠ FFFFFFFF | регистры не по спецификации → версия «сдвиг +8» |

## 7.21 Прогон stage 42 (2026-11-05): только чтения, гейт 26 МГц закрыт

```
USBv9 apmixed20=0003?BF0 gsnpsid=00000000
USBv9 infr2_sta=00000000 ckcfg8=02030300
USBv9 pw_ctl0=10411021   pw_sts1=00000000
USBv9 hcsp1=00000000     hccp1=00000000
USBv9 usbcmd=00000000    usbsts=00000000
USBv9 crcr=00000000      dcbap=00000000
USBv9 porte=00000000     dmon1=2A200000
```

- `apmixed20` = `AP_PLL_CON8`. Младший байт `0xF0` → **бит 4 = 1**, а гейт
  `APMIXED_SSUSB26M` инверсный (`GATE_APMIXED(..., 4)` + `ops_inv`):
  **26 МГц для SSUSB выключены**. Это и есть причина `GSNPSID=0` и вечного
  `CNR=1`: ядру DWC3 нечем завершить внутреннюю инициализацию.
- `ckcfg8 = 0x02030300` → `usb_top_sel` (биты [9:8]) = 3 и
  `ssusb_top_xhci_sel` ([17:16]) = 3 — муксы выставлены, тут всё в порядке.
- `infr2_sta=0`, `pw_sts1=0`, `pw_ctl0=0x10411021` — состояние «после LK»,
  гейты INFRA в этом прогоне намеренно не включались, поэтому DWC3 читается
  нулями (`hcsp1/hccp1/usbcmd/usbsts/crcr`) — это ожидаемо, а не новые данные.
- `dmon1=0x2A200000` → `HST_DISCON=1`, `LINE_STATE=00` (SE0): VBUS не подавали,
  устройство не подключено — нормально для этого прогона.

### Почему stage 41 уронил телефон

Запись была сделана **значением** `0x10`, а не read-modify-write. Это обнулило
все остальные биты `AP_PLL_CON8`, включая бит 8 (`MMSYS_F26M`) — дисплей
потерял 26 МГц: синий экран, зелёные артефакты, выключение. Вендорский драйвер
этот регистр правит именно RMW (`read & 0xfffff6af`) и даже закрывает его
комментарием `/* race condition access */`.

## 7.23 Прогон stage 43 (2026-11-06): RMW безопасен, но дело не в 26 МГц

Два результата:

### Разгадка: это не Synopsys DWC3

Из DTS (`ros_mt6785.dts`):

```
mtu3_0@11200000: reg = <0x11201000 0x3000>, <0x11203E00 0x100>
                 reg-names = "mac", "ippc"
                 clocks = <INFRACFG_AO_USB_CG>, <INFRACFG_AO_SSUSB_XHCI_CG>
xhci0@11200000:  compatible = "mediatek,mt67xx-xhci"
                 reg = <0x11200000 0x1000>
                 clocks = <INFRACFG_AO_SSUSB_XHCI_CG>
```

`mtu3_hw_regs.h` подтверждает: `SSUSB_DEV_BASE 0x0000`, `EPCTL_CSR 0x0800`,
`USB3_MAC_CSR 0x1400`, `USB2_CSR 0x2400` — всё относительно **0x11201000**, то
есть это **собственный MTK DRD MAC**, а не DWC3. Адрес `0x1120c120` (GSNPSID)
принадлежит Synopsys-ядру, которого в этой SoC просто нет. Поэтому:

- `GSNPSID = 0` — **не поломка**, регистра не существует;
- `HCSPARAMS1 = 0x0100020F` и `HCCPARAMS1 = 0x01400F99` с «невозможными» полями
  — это не «битый xHCI», а MTK-обёртка, у которой часть полей не по спеке;
- теория «ядро не клокнуто, поэтому CNR» **отменяется**.

Остаётся единственный реальный вопрос: почему контроллер не принимает
`CRCR`/`DCBAAP`/`CONFIG` и отвечает `TRB Error` на Enable Slot.

   трогали только `PW_CTRL0` (SW_RST) и `PW_CTRL1` (HOST_PDN).

## 7.27 Прогон stage 45 (2026-11-06): CNR снимает PHY, а регистры кольца — нет


Итоги:

- **`CNR` завязан на PHY.** Как только поднимается U2/U3 PHY
  (`usb_host_up`), `CNR` уходит в 0 и в варианте A, и в варианте B. В stage 44

### Рабочая гипотеза: CRCR и DCBAAP перепутаны

В stage 39 событие ошибки имело `ev0 = 0x400AB4C0` — это **ровно адрес
`x_dcbaa`**, то есть значение, которое мы записывали в `DCBAAP` (`op+0x18`).
Картина сходится, если в этой MTK-обёртке запись в `0x18` попадает в **CRCR**,
а в `0x10` — в `DCBAAP`: тогда наше «DCBAAP» становилось указателем командного
кольца, контроллер брал нулевой TRB оттуда и отвечал `TRB Error`.

## 7.28 Stage 46 (`usb_probe(46)`): какой offset — CRCR

Enable Slot не использует DCBAA, поэтому он идеальный дискриминатор:
программируем **только один** кандидат (`0x10` или `0x18`), DCBAA оставляем
нулевым, запускаем и смотрим, вернётся ли слот. `ev0` покажет, какой адрес
контроллер реально использовал.

```
USBvd cnr_sts=… rd=…        <- вариант 0x10
USBvd at=00000010 code=… 
USBvd slot=… ev0=…
USBvd cnr_sts=… rd=…        <- вариант 0x18
USBvd at=00000018 code=…
USBvd slot=… ev0=…
```

| Лог | Вывод |
|---|---|
| `at=10 code=1` | CRCR на `0x10` (по спеке); ломала его именно запись DCBAAP |
| `at=18 code=1` | перестановка подтверждена: CRCR=`0x18`, DCBAAP=`0x10` |
| оба `code=5` | ни один вариант; смотрим `ev0` — какой адрес он берёт |

## 7.29 Прогон stage 46 (2026-11-06): CRCR НАЙДЕН — 0x18

```

USBvd at=00000010 code=00000005        <- TRB Error, ev0=00000000
USBvd slot=00000001 ev0=00000000
USBvd cnr_sts=00000001 rd=00000000

USBvd slot=00000001 ev0=400AD3C0       <- ровно наш TRB (want было ...C1)
```

Дискриминатор сработал идеально: при программировании `0x18` **Enable Slot
прошёл** (`code=1`, `slot=1`), и `ev0` указывает точно на наш командный TRB
(`0x400AD3C0`), а не на `x_dcbaa`. При `0x10` — TRB Error с `ev0=0`.

**Итог: в MTK-обёртке (`mediatek,mt67xx-xhci`) 64-битный блок кольца сдвинут на
+8 байт относительно спецификации xHCI:**

| регистр | спека | здесь |
|---|---|---|
| CRCR (64 бит) | `0x10` | **`0x18`** |
| DCBAAP (64 бит) | `0x18` | **`0x20`** |
| CONFIG | `0x20` | **`0x28`** |

Отсюда же объяснение старого кода: `DCBAAP = op+0x20` и `CONFIG = op+0x28` были
записаны **верно** (автор их угадал), а `CRCR = op+0x14` — нет. Наша «правка по
спеке» (`0x10/0x18/0x20`) сдвинула всё вниз и сломала DCBAAP, поэтому
`enslot=5` и держался.

`xhci_ctrl_in()` каждый раз писал TRB по индексам 0/1/2 заново, а контроллер

(код 4). Исправлено: кольцо EP0 теперь **append-only** (`x_ep0_n`), 16 TRB дают
пять control-трансферов — ровно столько, сколько нужно для перечисления.

## 7.32 Прогон stage 47+ (2026-11-06): `cfg9=4` — не кольцо, а Chain bit

После append-only-фикса кольца EP0 картина не изменилась: `cfg9=4`
(USB Transaction Error), при этом `devdesc=1`, `vid_pid=09171F75`,
`mps0=0x40`. Значит дело не в переиспользовании TRB, а в **структуре TD**:

В xHCI control-трансфер с data-стадией — это один TD: `Setup Stage` (с
`Chain bit`, бит 4) → `Data Stage` (последний с `IOC`) → и отдельный TD
`Status Stage`. У нас Setup-TRB шёл **без Chain bit**: контроллер выполнил
setup и получил данные (дескриптор устройства прочитался!), но TD не
завершился — и следующий запрос упирается в `transaction error`.

Исправлено:

1. `Setup Stage` TRB: добавлен `Chain bit` (`1 << 4`).
2. Чтение config-дескриптора — с одним ретраем (многие устройства «отваливают»
   первый запрос после смены адреса).
3. Диагностика `cfgd0=`/`cfgd1=` — если данные всё же пришли, их видно.
4. Если код ≠ 1, но в буфере реально лежит configuration descriptor
   (`bLength >= 9`, `bDescriptorType == 2`), данные принимаются: некоторые
   контроллеры ругаются на хвостовую status-стадию, терять из-за этого
   дескриптор бессмысленно.

Образ: md5 `0d2f2493dae0783081b77fc03bc23814`.

## 7.33 Прогон stage 47++ (2026-11-06): TRT — вот чего не хватало

С добавленным `Chain bit` дескриптор устройства сломался: `devdesc=5`
(TRB Error), `vid_pid=0`. Это и подсказало причину: контроллер начал проверять
TD и увидел несогласованность. В `Setup Stage` TRB **не было выставлено поле
TRT (биты [17:16])** — оно означает тип data-стадии:

```
TRT = 0  -> нет data-стадии
TRT = 2  -> OUT
TRT = 3  -> IN
```

У нас TRT=0, то есть «data-стадии нет», а следом шёл Data TRB. Без `Chain bit`
контроллер это терпел (и первый запрос даже отдал данные), но TD не
завершался — отсюда `cfg9=4` на втором запросе; с `Chain bit` он честно
ответил TRB Error.

Правильная раскладка одного control-TD:

| TRB | поля |
|---|---|
| Setup | type 2, **TRT=3 (IN)**, IDT, **CH=1** |
| Data | type 3, **DIR=1**, IOC=1, CH=0 |
| Status | type 4, DIR=0 — отдельный TD |

Образ: md5 `4952ae1b3362f6f930154753d2cc80f1`.

## 7.34 Прогон stage 47+++ (2026-11-06): обёртка не любит chained TD

```
USBe devdesc=00000005 vid_pid=00000000   <- TRB Error, уже на первом запросе
```

С `TRT=3 + CH=1` обёртка отвергает TD целиком. Итого проверено:

| Setup TRB | результат |
|---|---|
| `TRT=0, CH=0` | дескриптор устройства **читается** (VID/PID верные), но второй запрос даёт код 4 |
| `TRT=0, CH=1` | TRB Error на первом запросе |
| `TRT=3, CH=1` | TRB Error на первом запросе |

Вывод: эта реализация выполняет setup / data / status как **три независимых TD**
и chained-TD не поддерживает. Значит рабочую конфигурацию (`TRT=0, CH=0`)
надо оставить, а причину `cfg9=4` искать в другом.

### Причина `cfg9=4` — «застрявшее» событие status-стадии

`xhci_ctrl_in()` ждал «любое transfer-event с endpoint ID = 1». Но status-стадия
каждого трансфера генерирует **своё** событие (и оно приходит с кодом 4). Первый
вызов возвращался по событию data-стадии (код 1 — дескриптор читался), а событие
status-стадии оставалось в кольце и на следующем вызове выдавалось за результат
нового запроса. Отсюда «cfg9=4» при полностью корректном дескрипторе устройства.

Исправлено в `xhci_ctrl_in()`:

1. **Дренаж** очереди событий перед каждым трансфером (выбрасываем остатки).
2. **Сопоставление по адресу TRB**: результат берётся только из события, у
   которого `ev0` равен адресу нашего data-TRB; событие status-стадии
   запоминается отдельно и используется лишь как fallback.

Образ: md5 `ec63e7adf4609380442d5ebf2a4bad71`.

## 7.35 Stage 47+диагностика (2026-11-06): измеряем, а не гадаем

Флаги TRB перебирались вслепую — это тупик. Вместо очередной догадки прогон
собирает три факта, которые закрывают вопрос:

1. **Дамп событий с адресами.** Каждый transfer-event теперь пишется в
   `x_evlog[]`, и в лог идут `ev0ad/ev0cd`, `ev1ad/ev1cd` — адрес TRB и код.
   Сравнив их с адресами наших TRB (`x_ep0[1]` = data, `x_ep0[2]` = status),
   видно, **какая именно стадия** даёт код 4.
2. **Состояние EP0 и слота — из device context в памяти.** Контроллер сам его
   пишет, так что `ep0_state()` (`x_devctx[8] & 7`: 1=Running, 2=Halted,
   3=Stopped) и `slot_state()` (`x_devctx[3] >> 27`: 2=Addressed,
   3=Configured) — это мнение железа, а не наше.
3. **Штатное лечение halt:** `Reset Endpoint` (тип 15, DCI 1) +
   `Set TR Dequeue Pointer` (тип 16) на следующий триплет, с печатью кодов
   обеих команд и повторной попыткой config-дескриптора.

Дополнительно возвращена та форма TRB, которая **доказанно** отдала корректный
дескриптор устройства (`dlen=18`, VID/PID Innostor).

| Лог | Что означает |
|---|---|
| `ep0st0=2` | EP0 в Halted → чинить halt (reset+setdeq) штатно |
| `ep0st0=1`, `ev0cd=4` на адресе data-TRB | ошибка в data-стадии (DIR/длина/MPS) |
| `ev1cd=4` на адресе status-TRB | обёртка не принимает отдельную status-стадию |
| `rst_ep=1, deq=1, cfg9b=1` | лечение сработало → встраиваем в штатный цикл |

Образ: md5 `c6b9610ff9ff58f4c89acc08b6f45a6b`.

## 7.36 Ключ к control-трансферам: «успех важнее кода»

Прогон с дампом событий дал решающий факт:

```
USBe devdesc=00000004 vid_pid=09171F75
```

Код 4, **но данные корректные** (VID/PID тот самый, dlen=18). Значит:

- data-стадия проходит и отдаёт данные;
- код 4 прилетает от **status-стадии** (отдельный TD, который эта обёртка
  не любит), и это событие висит в очереди;
- сопоставление по адресу TRB оказалось неверным (события успеха не
  распознавались), а «дренаж» `xhci_evt(ev, 0)` вообще не работал: при `ms=0`
  функция выходит по таймауту, не заглядывая в кольцо.

Исправлено в `xhci_ctrl_in()`:

1. Настоящий дренаж: `xhci_evt(ev, 1)` до 50 раз.
2. **Побеждает успех**: после doorbell берём первое событие с кодом 1; ошибка
   возвращается только если ни одного успешного не было.

Так поведение железа (data=1, status=4) перестаёт ломать логику.

### Эталон из Android/recovery

Параллельно есть точный способ закрыть вопрос без догадок — снять живой дамп
xHCI из работающей системы (root shell в OrangeFox):

```sh

ls -l /dev/mem                                        # доступен ли
# caps+op+port (0x11200000, 4 КиБ)

```

Если в recovery удастся перевести порт в host и подключить флешку, то из дампа
берутся `CRCR`/`DCBAAP` и по ним — содержимое колец в RAM: это и есть эталонный
формат TRB, который принимает именно эта обёртка.

## 7.37 Stage 47 (эталонные TRB): ПЕРЕЧИСЛЕНИЕ РАБОТАЕТ

Ровно та раскладка TRB, что в вендорском `xhci-ring.c` (setup `TRT=3|IDT`, data

```
USBe class=00000000 mps0=00000040
USBe dlen=00000012 dtype=00000001

```

Флешка: **VID 0x1F75 / PID 0x0917** (Innostor IS917), mass storage,
High Speed, bulk IN `0x81`, MPS 512.

Два дефекта разбора дескриптора исправлены: граница цикла `i + 8 < len`

### Что добавлено для BOT/SCSI (stage 47+)

1. `xhci_ctrl_nodata()` — control-трансфер без data-стадии (`TRT=0`,
   status DIR=IN), им отправляется **SET_CONFIGURATION(1)**; без него bulk
   эндпоинты не работают.
2. `ep_configure()` — команда Configure Endpoint (тип 12) с контекстами
   DCI 3 (bulk IN, тип 6) и DCI 4 (bulk OUT, тип 2), MPS из дескриптора.
3. `xhci_bulk()` — нормальный TRB на своём кольце на каждый эндпоинт,
   doorbell с номером DCI.
4. `bot()` — CBW (31 байт) → data → CSW (13 байт), возвращает `bCSWStatus`.
5. Команды: INQUIRY (36 байт), READ CAPACITY(10), READ(10) LBA 2 —
   сигнатура HFS+ лежит по смещению 1024 (`H+` = 0x482B, `HX` = 0x4858).

## 7.38 Прогон stage 47 (2026-11-06): другая флешка — тот же отказ

Проверка гипотезы «дело в Innostor IS917». Взят **другой накопитель**:
флешка USB-A через переходник на Type-C.

- VID/PID = `0x10008564` → **VID `0x8564` (Transcend), PID `0x1000`**.
- На флешке есть индикатор питания — **горит**, то есть VBUS под реальной
  нагрузкой есть (не только на холостом ADC).
- `vbus=0x231B` в этом прогоне **не сходится** с прежней формулой
  (raw × 6.25 мВ дало бы ≈ 56 В). Значит, читается другой канал/делитель,
  либо изменился смысл поля. Требует перепроверки перед тем, как ссылаться
  на это число; факт питания подтверждён индикатором, а не этой цифрой.
- Перечисление прошло **идентично** IS917: `dlen=0x12`, `class=0`,
  `mps0=0x40`, config len `0x20`, `ep_in=0x82`, `ep_out=0x02`,
  MPS 512/512, ifclass 8 / subcls 6 / proto `0x50`, `spd=3` (High Speed),
  `addr=1`, `slot=1`, `LAST_CTX+1 rule` воспроизведён, `both endpoints
  configured`.
- Контексты в RAM снова **нули**: `devctx0=0`, `devctx8=0`, `slot0=0` —
  контроллер не пишет device context ни для одного устройства.
- Bulk: `ing=FFFFFF9D` (−99, нет события за 4 с), `cap=FFFFFF9D`,
  `rd2=FFFFFF9D`, `sig=0` — **ровно как у IS917**, сигнатуры нет.

**Вывод:** отказ bulk не зависит от накопителя. Гипотеза «виноват IS917»
опровергнута (Вариант B исчерпан, результат отрицательный). Дефект лежит
в нашей host-реализации / в обёртке xHCI, а не в устройстве. При этом
control-трансферы (GET_DESCRIPTOR, SET_CONFIGURATION) проходят — значит
event ring и command ring рабочие, а не работает именно transfer ring
bulk-эндпоинтов.

Побочный вывод: питание флешки больше не вопрос — VBUS держится под
нагрузкой (индикатор), это подтверждено на втором устройстве.

### Stage 48 (`usb_probe(48)`)

Один прогон, последовательность:

1. Открыть гейты INFRA1 (бит 4 и 16), прочитать `infra1_sta`, `MSDC_CFG`.
2. Дамп `MSDC_PS`, `MSDC_INTEN`, регистров `msdc1_top` (0x11e10000).
3. Найти LDO-слейв, включить LDO5 (VMCH) и LDO3 (VMC) по 3.0 В, прочитать назад.
4. Перечитать `MSDC_PS` — `CDSTS` должен стать 1 (карта видна).
5. Минимальный `msdc_init_hw()`: `MODE|CKPDN|PIO`, сброс, `PATCH_BIT=0x403c0046`,

затем `ocr=80ff8000`-подобное с битом 31. Если `cd=0` — не смультиплексированы

## 7.40 Прогон stage 48 (2026-11-06): карта не питается, шина в нулях

```
SD  infra1_sta=00000000 cfg=02000099
SD  ps=00000002 inten=00000000
SD  top=00000000 top1=00000000
SD  ldo_probe=00000034 d5=FFFFFC00
SD  ldo_probe=00000075 d5=FFFFFF00
SD  ldo_probe=0000004E d5=FFFFFC00
SD  ldo5_en=00000000 ldo3_en=00000000
SD  ps_pwr=00000002 cd=00000001
SD  cfg=0000788B ckstb=00000001
SD  cmd0_int=00000100 sts=00000003
SD  cmd8_int=00000400 resp=00000000
SD  acmd41_int=00000000 ocr=00000000
```

Разбор:

- `infra1_sta=0` — гейты открыты (INFRA-гейты активно-низкие: 0 в STA = такт есть).
- `cfg=0x02000099` до наших записей — LK/прелоадер уже что-то настроил
  (MODE, PIO, CKDRVEN, CKSTB).
- `ps=0x2` — **CDSTS=1**, но `DAT[23:16]=0` и `CMD=0`: линии в нуле.
  У запитанной карты CMD/DAT подтянуты вверх, то есть должно быть 1.
- `ldo_probe`: все три адреса **отвечают ACK**, но чтение падало в −4 —
  это **баг в stage 48**, а не в железе: в `mt6360_ldo_read_device()`
  поток чтения это `[data][crc]`, эхо-байт **не читается**, он только
  подставляется в CRC как константа. Я же ждал `[echo][data][crc]`.
- Из-за этого `found=-1`, LDO5/LDO3 **не были включены** (`ldo5_en=0`),
  и карта осталась без питания.
- `cfg=0x788B` — наш делитель применён (биты 8..15 = 0x78 = 120), `ckstb=1`,
  то есть 400 кГц на выходе MSDC есть.
- `cmd0_int=0x100` (CMDRDY), но `sts=3` — контроллер считает шину занятой.
- `cmd8_int=0x400` — **RSPCRCERR**, а не CMDTMO. Значит MSDC снял 48 бит
  с линии CMD, но там нули (`resp=0`) — ровно то, что даёт неподтянутая
  линия. Это не ответ карты.
- `acmd41_int=0` — после ошибки CRC движок не выдал событий вообще.

Вывод: причина одна и понятная — **нет питания карты** (LDO не включён из-за
бага чтения). Пинмукс проверить всё равно стоит: ядро MSDC-пины не
мультиплексирует (`pinctrl-mt6785.c` не содержит MSDC-функций, а группы в
DTS задают только drive-strength), значит остаётся то, что оставил прелоадер.

### Stage 49 (`usb_probe(49)`)

1. Исправлено чтение LDO: `[data][crc]`, CRC по `[slave<<1|1, reg, data]`.
   Ошибки больше не маскируются: печатается `err_d` = код ошибки в старшем
   байте (−1..−5 = ACK адреса / ACK регистра / ACK чтения / CRC).
2. Порядок проб — `0x75, 0x34, 0x4e`, останов на первом CRC-валидном
   (0x75 — ожидаемый адрес LDO-страницы; так мы не пишем 0x40 в регистр
   зарядника на 0x34).
3. Включение LDO5 (бит 6 рег. 0x0b) и LDO3 (бит 6 рег. 0x05) + чтение назад.
4. **Пинмукс**: печать `MODE` для GPIO-групп 134..139, затем принудительная

   DAT0 137, DAT2 138, DAT1 139), затем повторный дамп `MODE`.
5. `MSDC_PS` — после питания `dat` должен стать `0xFF`, а CMD — 1.
6. `msdc_bringup()` (400 кГц), CMD0 → CMD8 → CMD55/ACMD41 ×20.
7. Дальше без данных: **CMD2** (CID, R2), **CMD3** (RCA, R6), **CMD9**

Ожидаемое: `cmd8_int=100 resp=000001aa`, затем `acmd41 ocr` с битом 31,
`cid0=…`, `rca=0001`, `csd_ver=1`, `mb=<объём карты>`.

Образ: `shim/out/shim-usbdiag-full.img`, md5 **`3da575f7bb3f5b958715cd24910c3a15`**.

## 7.41 Возврат на USB-C: stage 60 — карта регистров и записи контекстов

Повод: лог с флешкой Transcend (§7.38) доказал, что отказ bulk не зависит от
накопителя. Ветка xHCI была закрыта по неверному основанию («виноват IS917»),
поэтому возвращаемся к ней с измерениями, а не с гипотезами.

### Расхождение, которое видно прямо в коде

По спецификации xHCI при `caplen = 0x20`:

| Регистр | Спека | В нашем коде |
|---|---|---|
| USBCMD | 0x00 | 0x00 ✓ |
| CRCR (64) | **0x18** | 0x18 ✓ (именно он и «заработал» в stage 46) |
| DCBAAP (64) | **0x30** | `XO_DCBAAP = 0x28` ✗ |
| CONFIG | **0x38** | `XO_CONFIG = 0x20` ✗ |

CRCR = 0x18 — это и есть спека, а не «сдвиг +8». Значит модель «обёртка
сдвинута на 8» неверна хотя бы для одного регистра, и два других мы, судя по
всему, писали не туда. Это идеально объясняет наблюдение «Address Device
вернул Success, а контексты в RAM нули»: команда завершилась, но записывать
ей было некуда, а EP0-кольцо обёртка запомнила у себя, поэтому control-трансферы
и шли.

Утверждать это без измерения нельзя — offsets проверяются одним прогоном.

### Stage 60 (`usb_probe(60)`)

Полный путь stage 47 (питание, PHY, host, перечисление, BOT) плюс
инструментация, всего ~10 дополнительных строк:

1. `DReg at28= at30=` и `DReg at38= crcr=` — что реально лежит в регистрах
   после Address Device.
2. `DReg dcbaa0= dcbaa2=` — что мы записали в таблицу DCBAA.
3. `DCtx nz= first= / fv= w8=` — **сигнатура области контекстов**: сколько
   слов из 256 непустых, индекс первого непустого и его значение. Пустая
   сигнатура = контроллер не писал вообще; `first≠0` = писал со сдвигом.
4. `DReg2` + `DCtx2` — то же после Configure Endpoint.
5. `MAP rd28= rd30= / rd38=` — контроллер остановлен, в 0x28/0x30/0x38
   записаны маркеры `a5a50028/30/38` и прочитаны назад: видно, какой оффсет
   держит запись, а какой игнорируется (или алиасится).

### Как читать результат

| Наблюдение | Вывод |
|---|---|
| `rd30=a5a50030`, `rd28` не менялся | DCBAAP действительно 0x30 → правим offsets, дальше bulk |
| `rd28=a5a50028`, `rd30` не менялся | обёртка правда сдвинута, но не на +8 системно → перестраиваем модель |
| оба держат запись | алиасинг: несколько оффсетов смотрят в один регистр |
| ни один не держит | DCBAA программируется не через op-регистр (искать в IPPC/ином блоке) |
| `DCtx nz>0, first≠0` | контроллер пишет контексты по другой раскладке — тогда дампим окно вокруг `first` |

Образ: `shim/out/shim-usbdiag-full.img`, md5 **`f6ee7d5acb976da30232d26e293d3566`**.

Ветка microSD припаркована: код `sd_stage48/49` остаётся в `usb.c`, образ
`3da575f7bb3f5b958715cd24910c3a15` при необходимости пересобирается одним
`build.sh`.

## 8. Практическая рекомендация

1. Прошить `shim/out/shim-usbdiag.img` (30 с, ничего не пишет) и снять фото —
   это отвечает на главный неизвестный вопрос: жив ли DWC3 после LK, и берёт ли
   он host-режим.
2. Если `gsnpsid` мусорный — сначала bring-up питания/клоков USB (это
   блокирующее для всех USB-сценариев, включая лог через USB-ECM).
3. Параллельно не бросать microSD: это единственный путь, который реально
   доводит до `hfs: mounted` за дни, а не недели.

## 7.42 Прогон «диагностика зависания после AKS» (2026-11-08): патчи 0098–0101

**Симптом.** Ядро печатает `ROSEMARY AKS: AppleKeyStore registered (no passcode,
unlocked)` и останавливается; маркеры `bsd_init`/`IOKitBSDInit` не появляются,
затем телефон уходит в перезагрузку. Полного лога нет: UART не выведен, ADB при
живом XNU нет, DRAM после сброса не сохраняется (канарейка шима это показала —
но сброс был по долгому нажатию питания, то есть power cycle; см. ниже).

**Три приёма в одной сборке.**

1. `0099-rosemary-iokit-sweep-markers` — `ROSEMARY IOKIT: StartIOKitMatching
   enter` / `returned` в `iokit/Kernel/IOStartIOKit.cpp` (файл, который не
   трогает больше ни один патч, поэтому ханк применяется всегда).
2. `0100-rosemary-match-trace` — печать каждого кандидата IOKit:
   `ROSEMARY MATCH: <сервис> <- <провайдер>` перед `startCandidate()` и
   `ROSEMARY MATCH: <сервис> started 0|1` после. Если строка `started`
   не появилась — встал именно этот драйвер; если не появилась даже пара
   `<-` — встал сам цикл сопоставления (тогда смотреть 0099: `returned` нет).
3. `0101-rosemary-boot-heartbeat-pager` (`bsd/dev/rosemary_beat.c`) — поток,
   который раз в секунду печатает точку и раз в 15 тиков строку
   `ROSEMARY BEAT N`, а через 40 с начинает выкладывать на экран кольцо
   консоли (4 МиБ, кормится из `_cnputs`): 60–75 строк на страницу,
   `ROSEMARY LOGPAGE: bytes A..B of T`, от хвоста назад до самого старого
   байта и по кругу. Страницы фотографируются и читаются оффлайн.
   Boot-args: `rosemarybeat=`, `rosemarypage=40`, `rosemarypageevery=20`
   (`rosemarypageevery=0` — только пульс, без страниц).
4. `0098-rosemary-log-ring-readers` — `rosemary_bootlog_position()` /
   `rosemary_bootlog_copy()`: чтение кольца без блокировок (страницы может
   писать другой CPU, пока bootstrap-поток стоит) плюс флаг
   `rosemary_log_pause`, чтобы пагер не переписывал собственный вывод.

**Как читать экран.**

| Наблюдение | Вывод |
|---|---|
| точки идут после последней строки драйвера, страницы идут | ядро живо, стоит bootstrap-поток → виноват драйвер из `LOGPAGE` |
| точки идут, `started` для следующего кандидата нет | зависание внутри `start()` этого кандидата |
| точки остановились сразу после AKS | спин с выключенными прерываниями (или умерла консоль) → нужен более дробный маркер внутри AKS/сразу после |
| `ROSPAGE` идёт, но `MATCH` пуст | `StartIOKitMatching` не дошёл до кандидатов — смотреть `InitIOKit`/`ConfigureIOKit` |

**Шайм: две половины эксперимента с DRAM.** Обычная сборка по-прежнему
выключает watchdog перед прыжком (`wdt_disable`), поэтому зависание
заканчивается долгим нажатием питания — а это power cycle, DRAM теряется
всегда, и прежний вывод «DRAM не выживает» ничего не доказывал. Сборка
`-DSHIM_KEEP_WDT` (`shim/out/shim-xnu-wdt.img`) оставляет watchdog взведённым:
зависание даёт **тёплый** сброс, и следующий запуск шима печатает
`CANARY prev=` и, если лог нашёлся, копирует его в `expdb` (LBA 776; `boot_b`
из списка целей убран — туда писали старт загрузочного образа).

**Порядок.** (1) обычный образ → фото пульса и страниц; (2) образ `-wdt` →
один прогон до зависания, затем второй запуск и чтение `CANARY`; если DRAM
выжил — переносим 4-МиБ кольцо в `expdb` и логи больше не фотографируем.

### 7.42.1 Результат прогона k23 (2026-11-08): AKS пройден, но телефон сбрасывается

Ядро 23 с настоящим кодом (кеш объектов v3 снял «замороженные» объекты) прошло
дальше, чем когда-либо:

```
ROSEMARY IOKit: StartIOKitMatching enter
ROSEMARY MATCH: RosemaryPlatformExpert <- D22AP      ... started 1
ROSEMARY MATCH: AppleKeyStore <- IOResources         ... started 1
ROSEMARY MATCH: IOWatchdog <- IOResources            ... started 1
ROSEMARY MATCH: IOCoreSurfaceRoot <- IOResources     ... started 1
ROSEMARY MATCH: RosemaryHIDButtons / HIDTouch        ... started 1
ROSEMARY MATCH: AppleCLCD <- disp0                   ... started 1
ROSEMARY IOKit: StartIOKitMatching returned
../../..........ROSEMARY BEAT 15
zone_init: map GEN0…DATA…, VM bootstrap done, IOKit IOMD setownership ENABLED
```

То есть блокер «стоит на AppleKeyStore» был артефактом кеша объектов: патч
`no_aks` в ядро не попадал. Реальная смерть — позже и без паники: последняя
строка на экране, затем сброс в загрузчик через ~25–30 с.

Что это значит:

- паники нет (её текст печатается) → либо спин/сброс железа, либо смерть до
  того, как консоль успела что-то сказать;
- 25–30 с — ровно тот интервал, на который шайм взводил A7 WDT
  (`wdt_init_long_timeout`, длина 0xfff), а `wdt_disable()` снимает только бит
  `EN` **этого** экземпляра: либо он не сработал, либо LK/PMIC держат второй;
- битые/склеенные строки в логе (`ROSEMARY IOKit` вместо `IOKIT`, обрыв
  `…subsystem is initialized`) — следствие того, что поток пульса печатал точки
  посреди `kprintf` bootstrap-потока.

Поэтому в сборку добавлено: поглаживание top RGU (`0x10007000 + 8`, ключ
`0x1971`) раз в тик с печатью `ROSEMARY WDT: mode= length=`, печать фазы
`ROSEMARY PHASE: <имя>` на каждом переходе startup-подсистемы и правило «точка
только если консоль молчала весь тик».
